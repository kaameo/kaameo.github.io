## 문제 상황

- 고객사 서비스를 운영하는 EKS 클러스터 관련 비용만 **월 약 $2,307**이었습니다.
- Cost Explorer의 비용과 클러스터의 실제 사용량을 대조해 보니, 사양이 섞여 있던 일반 노드 7대(`r6i.xlarge`, `m6i.xlarge`, `t3.large`, 총 144GiB)의 CPU 사용률은 2~13%, <strong>메모리 사용률은 44~62%</strong>였습니다.
- 미사용 NLB와 외부 ElastiCache 등 과도하게 프로비저닝된 부가 리소스 비용도 함께 발생하고 있었습니다.
- 계약 특성상 6개월 뒤 클러스터가 종료될 가능성이 있어, 최소 1년 약정인 Savings Plan으로는 비용을 줄일 수 없었습니다.

## 접근 방식

![EKS 재설계 전후](/portfolio/eks-cost-before-after.png)

- 비용을 인스턴스, EBS, AZ 간 전송, 로드밸런서, ElastiCache 같은 항목 단위로 나누고 `kubectl top`으로 **실제 사용량을 측정**했습니다.
- CPU 사용량이 큰 데이터 변환 엔진용 전용 노드(`c6i.xlarge`) 1대는 유지하고, 검색 엔진의 heap 상한을 12Gi → 8Gi로 낮춘 뒤 일반 노드 7대(총 144GiB)를 **메모리 중심 노드(`r6i.xlarge`) 3대로 통합**했습니다.
- 외부 ElastiCache를 제거해 **클러스터 내부 Valkey로 대체**하고, 미사용 NLB를 정리했습니다.
- **월 총액과 장애 시나리오로 대안을 비교**했습니다. 스팟 인스턴스(약 65% 할인)는 stateful 계층이 한꺼번에 회수될 수 있고, 단일 AZ는 AZ 하나의 장애가 서비스 전체 중단으로 번질 수 있어 제외했습니다.
- 월 $100~170의 AZ 간 전송비를 감수하고 3개 AZ에 1대씩 배치하는 안을 선택해 운영 중인 기존 클러스터를 축소한 뒤, 서비스의 실제 기능 전반이 **정상 동작하는지 확인**했습니다.

## 해결 및 성과

| 항목 | 이전 (2026. 06) | 이후 (2026. 07) |
| --- | --- | --- |
| EKS 관련 월 청구액 | 약 $2,307 | 약 $1,100 (약 52% 절감) |
| EC2 노드 | 8대 (7대 + CPU 전용 1대) | 4대 (3대 + CPU 전용 1대) |

- stateful replica 3개를 AZ마다 하나씩 두는 **3AZ 배치를 유지**했습니다.
- 대안 비교와 기각 이유, 전환 위험 항목을 문서로 남겨 팀에 공유하고, 이후 재구축 시 인프라 기준과 인수인계 자료로 사용했습니다.
