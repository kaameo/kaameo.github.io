## 문제 상황

- 파일 업로드를 위해 사용자 PC가 Presigned URL로 S3에 직접 업로드하는 구조를 설계했습니다.
- 같은 URL로 EC2 업로드와 외부 PC의 Presigned GET은 성공했지만, **외부 PC의 Presigned PUT만 6바이트에서도 `403 AccessDenied`로 거절**됐습니다.
- 서명, 만료, IAM 정책 시뮬레이터에서 이상이 없어 AWS 조직 정책(SCP/RCP)으로 추정했지만, 정책을 조회하거나 바꿀 권한이 없었습니다.

## 접근 방식

![업로드 경로 전후 비교](/portfolio/hapbang-s3-upload-before-after.png)

- 현재 권한에서 업로드가 가능한 EC2를 경유하도록 바꿨습니다. **2GB 본문을 메모리에 모으지 않고 S3로 스트리밍**하고, DB 트랜잭션은 권한과 파일 정보 검증, 완료 상태 변경에만 짧게 사용했습니다.
- Envoy는 업로드 경로에만 버퍼링을 끄고 장시간 전송을 허용했습니다. 일반 API의 제한은 유지하고, 앱에서 2GB 상한을 검사했습니다.
- 서버 네트워크와 요청 스레드를 점유하는 비용이 생겨 pod별 동시 업로드를 20개로 제한하고, 초과하면 503으로 거절했습니다. 되감을 수 없는 입력 스트림의 SDK 자동 재시도는 끄고, 실패 시 클라이언트가 처음부터 재업로드하도록 했습니다.

## 해결 및 성과

- 운영 환경(외부 PC → Envoy → lecture-app → S3)에서 단일 **2GB 영상 업로드를 8분 17초 만에 완료**했습니다.
- 업로드 중 컨테이너 메모리 사용량(working set)은 <strong>630.2 → 636.9MiB(+6.7MiB)</strong>에 그쳐, 704MiB 메모리 한도 안에서 2GB 파일을 안정적으로 처리했습니다.
- 업로드 전후의 **JVM heap 사용량도 동일한 범위로 유지**됨을 확인했습니다.
