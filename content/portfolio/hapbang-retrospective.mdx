## 협업 방식

- **변경 영향 선제 공유:** 다른 팀원의 작업에 영향을 주는 변경은 문서로 먼저 설명했습니다. S3 업로드가 서버 경유로 바뀌었을 때 바뀐 요청 순서, 예시 코드, 오류 응답을 팀 공지로 정리해 연동 혼선을 줄였습니다.
- **실수를 시스템으로 방지:** 기능 브랜치가 리뷰 없이 `main`에 병합된 사고 직후 병합을 되돌리고, `main`으로 가는 PR은 `dev`에서 온 것만 통과하는 CI 필수 체크를 추가했습니다.
- **팀 개발 환경과 규칙 정비:** 초반에 커밋 컨벤션, 브랜치 규칙(`feature/tkt-<이슈 번호>`), 응답 스키마 규칙을 합의해 끝까지 지켰고, PR 자동 리뷰(Claude)와 문서 인덱싱 구조로 팀의 AI 개발 환경을 구축했습니다.

## 회고와 개선

- **눈높이를 맞춘 기술 소통:** 현업 경험 기준으로 인프라와 설계를 설명하다 보니 배경 지식이 다른 팀원이 논의를 따라가기 어렵다는 피드백을 받았습니다. 해결책을 바로 제시하기 전에 배경과 용어를 문서와 다이어그램으로 먼저 맞추는 소통의 중요성을 배웠습니다.
- **경계 중심 설계 시야:** 계층 구조(Controller/Service/Repository)에 익숙해 모듈 경계를 나누는 것에 시행착오가 있었지만, 바운디드 컨텍스트와 계약(ArchUnit)을 먼저 잡아야 분리 비용이 줄어든다는 것을 체감했습니다.
- **인터페이스 선확정으로 병목 방지:** 백엔드, 인프라, 프론트엔드를 병행하며 일정 산정이 어긋나 팀원의 병목이 된 구간이 있었습니다. 여러 역할을 맡을수록 다른 팀원이 의존하는 API 계약을 먼저 확정하고 작업을 작게 쪼개 조율하는 방식으로 보완하려 합니다.

## 동료 피드백

- **방향 제시와 주도성:** 설계와 구현에서 적극적으로 의견을 내며 팀원들의 고민에 방향을 제시했고, 기획과 코드 외 작업과 꼼꼼한 피드백으로 프로젝트의 빈틈을 채워 줬다는 평가를 받았습니다.
- **팀 정렬과 경험 공유:** 프로젝트의 큰 흐름을 잘 맞추고 인프라와 현업 경험을 공유해, 팀원들이 자신감을 가지고 맡은 업무를 수행할 수 있었다는 피드백을 받았습니다.
