## 문제 상황

![작업 유실 문제](/portfolio/redis-streams-loss-problem.png)

- 오케스트레이터가 수집 작업을 만들어 Redis Streams 작업 큐에 넣으면 Worker가 이를 꺼내 처리하는 구조였습니다.
- 간헐적으로 수집이 멈춰 DB를 보니 시작되지 않은 `queued` 기록이 쌓여 있었지만, 나중에 넣은 작업은 성공했고 에러 로그도 없었습니다.
- Redis에서 전달되지 않은 작업 수(consumer group lag)와 DB에서 시작되지 않은 `queued` 기록이 둘 다 80,375건인데 큐는 비어 있어, Worker에 전달되기 전 큐에서 삭제됐다고 추정했습니다.
- 보안 사건 1건 하위의 여러 알림을 개별 작업으로 fan-out하는 구조라 작업이 순간적으로 몰리면 길이 상한(MAXLEN 1,000건)을 넘어 오래된 미전달 작업부터 삭제(trim)됐고, 이는 Redis 정상 동작이라 **에러 로그가 남지 않았습니다.**

## 접근 방식

![작업 유실 해결](/portfolio/redis-streams-loss-solution.png)

- Redis 메모리 보호를 위해 상한은 유지하되 fan-out 버스트(6천 건/분 기준)를 흡수하도록 **작업 큐 상한을 1,000건에서 100,000건**으로 늘렸습니다.
- 상한만 늘린 다음 날 lag가 분당 약 1,000건씩 늘어 Worker 2개로는 몰리는 작업을 따라가지 못함을 확인했습니다. **Worker를 HPA로 전환하고 최소 5개로 늘려** 6천 건을 약 7분 안에 처리하게 했습니다.
- 상한 초과나 Redis 재시작으로 큐에서 작업이 유실돼도 영구 누락되지 않도록, DB에 남은 미시작 `queued` 기록을 **10분 뒤 `timed_out`으로 자동 전환해 재수집**하게 했습니다.
- 큐 길이, lag, `queued` 최장 대기 시간을 지표로 내보내고, **적체가 30분 이상 지속되면 Slack으로 알렸습니다**.

## 해결 및 성과

- **유실된 수집 작업 80,375건을 재수집**하고, 해당 기간 수집 건수를 보안 벤더 콘솔의 원천 건수와 대조해 모두 가져온 것을 확인했습니다.
- 최종 안정화 배포 이후 약 5일간 오케스트레이터가 큐에 넣은 작업과 Worker가 처리한 작업이 집계상 각각 **45,701건으로 같았고, Streams의 lag는 0, 큐 길이는 2건 이하**로 유지됐습니다.
- 미시작 기록을 운영 SQL로 직접 정리하던 절차를 **자동 회수**로 바꿔, 평소 운영에서는 수동 정리가 필요 없게 했습니다.
