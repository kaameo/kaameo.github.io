## 문제 상황

![기존 수집 구조](/portfolio/crawler-architecture-before.png)

- 기존 수집기는 하나의 고객사/벤더 전용이라, 수집 대상을 추가할 때마다 별도 프로젝트로 구현하고 배포해야 했습니다.
- 이 구조로는 고객사와 보안 벤더가 늘어나는 요구사항에 맞춰 같은 형태의 수집 코드가 계속 중복될 가능성이 컸습니다.
- 여러 고객사와 벤더를 하나의 플랫폼에서 지원하기 위해 고객사와 보안 벤더의 연결인 '연동'마다 자격증명을 관리해야 했습니다.
- 한 연동이 API 호출 한도를 넘어도 다른 연동의 수집은 막히지 않아야 했습니다.

## 접근 방식

![수집 플랫폼 아키텍처](/portfolio/crawler-architecture.png)

- 고객사/벤더마다 별도 배포하는 방식 대신, **하나의 멀티테넌트 플랫폼으로 통합**했습니다.
- 연동마다 자격증명과 수집 대상을 관리하도록 모델링했습니다. **자격증명을 암호화해 저장**하고, 기존 연동을 갱신할 때 고객사와 벤더가 일치하는지 검증했습니다.
- 벤더/데이터 유형별 수집 로직을 구현체로 분리하고 Registry에 등록하도록 설계했습니다. 벤더별 설정과 수집 대상도 등록 정보로 옮겨, 공통 제어 로직에 흩어져 있던 벤더별 분기를 제거했습니다.
- 호출 한도 초과가 반복되던 벤더 엔드포인트에 **Redis 기반 연동별 대기 시간**을 적용했습니다. 429 응답을 받으면 Retry-After를 기준으로 해당 연동의 동일 엔드포인트 호출을 제한하고, 다른 연동에는 같은 제한이 적용되지 않도록 했습니다.

## 해결 및 성과

- **4개 보안 벤더**를 하나의 플랫폼에서 지원했습니다. 운영자는 이 플랫폼에서 고객사별 연동과 수집 상태를 관리할 수 있었습니다.
- 공통 인터페이스를 재사용해 신규 벤더 1곳 추가 기간을 **기존 약 3주에서 약 1주로 단축**하고 실제 벤더 API로 검증했습니다.
- 안정화 배포 이후 15일간 실제 고객사 2곳과 테스트 테넌트 환경에서 **약 65만 건을 안정적으로 수집**했습니다.
