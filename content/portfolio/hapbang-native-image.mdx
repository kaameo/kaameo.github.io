## 문제 상황

- EC2 2대로 구성한 k3s 환경에 계획했던 앱을 더 배포해야 했지만, 실행 중인 앱과 관측 도구의 메모리 할당량이 노드 용량 대부분을 차지하고 있었습니다.
- 교육 과정에서 받은 AWS 계정이라 인스턴스 추가는 메모리를 더 줄일 수 없을 때만 요청할 수 있어, 먼저 기존 앱의 메모리 할당량을 줄여야 했습니다.

## 접근 방식

![고객센터 앱 메모리 할당량](/portfolio/native-image-memory.png)

<small>고객센터 앱의 메모리 requests/limits 설정값과 256MiB 예산 구성</small>

- JVM은 max heap을 조정해도 **앱마다 280~355MiB인 off-heap이 그대로 남습니다.** 그래서 Metaspace와 JIT 코드 캐시가 없는 Native Image를 선택하고, 트래픽과 외부 연동이 가장 적은 고객센터 앱부터 전환했습니다.
- Native Image로 바꾼 뒤 회귀 테스트 212개는 통과했지만 smoke test는 실패했습니다. Native Image는 JVM과 달리 빌드 때 등록된 타입에만 reflection/직렬화를 허용하기 때문입니다. 그중 Kafka listener가 멈춘 문제는 tracing agent로 필요한 타입을 찾아 등록해 해결했습니다.
- 운영 5시간 heap 사용량 최대 약 84MiB를 확인하고 max heap을 128MiB로 정했습니다. 여기에 off-heap과 page cache를 더한 약 227MiB에 맞춰 **requests와 limit을 448 → 256MiB로 낮췄습니다.**

## 해결 및 성과

- 노드 requests 합계를 3,712 → 3,520MiB로 줄여 **배치 여유 192MiB를 확보**했습니다.
- 다른 앱까지 전환하면 앱마다 CI가 10~14분 늘어 개발 속도가 느려지고, 메타데이터 검증도 반복해야 했습니다. 그래서 고객센터 앱만 Native로 유지하고, 다른 앱은 JVM max heap과 할당량을 조정해 메모리를 확보했습니다.
- 두 방식으로 확보한 자원으로 **계획했던 검색/알림 등을 담당할 앱을 배포**했습니다.
- 실제 메모리 사용량(working set)은 JVM 391MiB에서 Native 최대 123MiB로 줄었습니다.
- 기동 시간은 JVM 23~28초에서 Native 1.10~1.16초로 줄었습니다.
