## TL;DR

- "아직도 코드를 보세요?"라는 질문 앞에서 나는 **'아직은' 봐야 한다는 쪽**이다. 모든 코드를 사람이 리뷰하자는 뜻은 아니고, 어차피 이미 높아진 생산성을 되돌리는 것도 불가능하다.
- LLM은 확률적이고, 당장 돌아가는 코드만 쌓는 AI에게 주도권을 전부 넘기면 1~2년 뒤엔 되돌릴 수 없는 복잡성이 남는다.
- 10만 줄짜리 프로젝트를 진행하면서 95%는 보지 않았다. 그럼에도 문제가 생겼을 때 책임지고, 복잡성이 무너지기 전에 리팩터링할 **주도권**을 잃지 않기 위해 '아직은' 코드를 읽어야 한다고 생각한다.

요즘 SNS를 보면 개발자들을 소위 "긁는" 어그로성 게시글이 여러 개 있다. "html은 프로그래밍 언어다" 등등

2026년을 지나며 가장 핫했던 토픽은 "**아직도 코드를 보세요?**"라고 생각한다.

일단 나는 '아직은' 봐야 한다는 쪽이다. 코드를 알고 이해한다는 건 예측된 문제를 내가 해결할 수 있다는 뜻이다. 즉 내가 이 소프트웨어와 코드의 주도권을 쥐고 있다는 뜻이고, 주도권을 쥐고 있다는 건 이 코드에 대한 책임을 진다는 뜻이다.

## 주도권과 책임: 핸들 없는 차와 미트 프록시

주도권을 쥔다는것은 마치 차량의 핸들을 쥐는것과 같다.

![사이버캡](/posts/why-i-still-read-code/tesla-cybercap-1.png) ![사이버캡 내부](/posts/why-i-still-read-code/tesla-cybercap-2.png)

> 테슬라 사이버캡 핸들 없는데, 비슷하게 코드도 안 보는 시대가 올 거임

최근 테슬라가 핸들과 페달이 없는 자율주행 차량 사이버캡의 개인 주문을 열었다. 차량 가격 29,990달러(한화 약 4,000만 원)에 월 299달러 자율주행 구독이 필수이고, 아직은 일부 초청 고객과 특정 지역에 한정된 이야기다. 눈에 띄는 건 약관이다. 자율주행 중 사고가 났을 때 누가 책임지는지는 모호하게 비워둔 채, 보험과 법규 준수, 차량의 안전한 운행 책임은 차주에게 남겨뒀다.

자율주행과 LLM은 바닥부터 다른 기술이지만, 굳이 나란히 놓고 보면 닮은 구석이 있다. 핸들(코드)은 없애려 하면서도 막상 문제가 생겼을 때의 책임은 여전히 운전자(개발자)에게 남는다는 점이다.

~~운전을 못하는데 운전자라고 할 수 있나?~~

개발자에겐 이런 대화가 비슷하게 종종 벌어진다.

> **나:** 간단한 날짜 표시 기능인데 외부 라이브러리를 새로 추가하셨던데, 왜 쓰셨어요?
>
> **동료:** 그거 AI가 해준 거라 잘 모르겠어요.
>
> **나:** 아, 넵...
>
> *(5분 뒤)*
>
> **동료:** 아, 시간대 변환을 직접 짜면 버그가 잘 나서 라이브러리를 썼어요.
>
> **나:** 음, 우리 서비스는 한국 시간만 쓰는데 기본 내장 함수로도 충분하지 않나요?
>
> **동료:** 어, 잠시만요.
>
> *(5분 뒤)*
>
> **동료:** 아, 다른 모듈에서도 이미 그 라이브러리 형식으로 날짜를 주고받고 있어서 맞춰야 한대요.

이런 대화를 겪고 나면 "정말 코드를 몰라도 괜찮을까?"라는 의문이 남는다.

AI가 나오기 전 개발자들의 자조 섞인 밈 중 'JSON 상하차'라는 말이 있었다. 요즘 SNS에서는 '미트 프록시(Meat Proxy)'라는 말이 간혹 보인다.
JSON 상하차도 정말 잘 지었다고 생각했는데, AI의 답변을 그대로 전달하는 전달하는 사람을 '미트 프록시'로 부르는게 좀 가볍게 다가오진 않았다.

위 대화의 동료는 개발 지식이 부족한 사람이 아니다. 코드가 어떻게 작성되어 있고 어떤 아키텍처로 이어져 있는지 모르기 때문에 이런 대답이 나온다. AI에게 주도권을 넘겨버리면 "잠시만요, AI한테 물어볼게요" 이런 대화만 생긴다. 이럴거면 내가 AI한테 물어봤지.

## 내가 '기술자'라서 놓지 못하는 건 아닐까

![영화 〈어쩔수가없다〉 (박찬욱, 2025) 中 "난 기술자야!"라고 외치는 장면](/posts/why-i-still-read-code/i-am-engineer.png)

<small>영화 〈어쩔수가없다〉 (박찬욱, 2025) 中 "난 기술자야!"라고 외치는 장면</small>

그럼에도 이해하고자 나 스스로를 의심해봤다. 혹시 나 자신을 소프트웨어 **엔지니어**라고 생각하기 때문에 코드 보는 걸 놓지 못하는 건 아닐까.

AI가 등장하면서 개발자는 한층 더 고차원의 설계만 하면 된다는 말이 나온다. 과거에 어셈블리 대신 C 언어로 한 단계 높은 추상화에서 개발하게 된 것처럼, 이제는 스펙만 명시하고 구현은 AI에게 맡기면 된다는 주장이다.

얼핏 일리는 있다만 명확하게 이해되진 않는다.

**LLM은 컴파일러와 달리 확률적이다.** 같은 C 언어 파일 두 개를 컴파일하면 늘 동일한 어셈블리가 나온다. 반면 AI에게 같은 입력을 넣으면 매번 조금씩 다른 출력이 나온다. 계산기에 비유해 봐도 그렇다. 계산기가 있음에도 우리가 수학을 배우는 이유는 단순히 계산을 하기 위해서가 아니다. 그리고 계산기는 적어도 같은 입력에 같은 출력이 나온다.

**스펙의 모호함 문제다.**

> 그건 스펙을 너무 모호하게 써서 그래. 조금만 상세하가 쓰면 해결됨

하지만 소프트웨어와 시스템의 스펙을 자연어로 적으면서 모호함을 끝까지 없애다 보면, 그 문서는 결국 코드가 된다. Thoughtworks의 글([Should we still design code for humans?](https://www.thoughtworks.com/insights/blog/programming-languages/should-still-design-code-humans))의 내용을 참고했다. 모호함을 걷어낸 자연어 스펙은 결국 더 다루기 힘든 또 하나의 프로그래밍 언어가 될 뿐이다.

## 그렇다고 사람이 다 보는 건 병목 아닌가

AI로 끌어올린 생산성에 사람이 일일이 검토하는 건 무조건 병목이다. 실제로 655개 기업 데이터를 분석한 [하버드 연구진의 논문](https://news.hada.io/topic?id=37405)을 보면, AI 코딩 에이전트 도입 후 작성된 코드량은 44% 늘었지만 PR 머지 시간은 56% 길어졌고 실제 완료된 작업량은 크게 늘지 않았다. 병목이 코드 작성에서 코드 리뷰로 옮겨간 셈이다. 리뷰한다고 내가 굳이 병목을 만들어야 하나 싶은 생각이 드는 것도 당연하다.

결국 AI가 만들어내는 막대한 코드를 어떻게든 따라가야 한다. 나만 그렇게 느낀 건 아닌지 이런 간극을 메우려는 도구들도 여럿 나왔다. 나는 `git push` 전에 AI가 짠 코드의 동작과 예외 상황을 퀴즈로 확인해 주는 [`sphinx`](https://github.com/parthh01/sphinx) 같은 도구를 써보고 있다.

> AI 코드 리뷰를 2중, 3중으로 두면 결국 버그는 찾는다

이 말에도 꽤 공감한다. 실제로 AI리뷰를 여러번 돌리면 웬만한 버그는 잡힌다.

여기까지만 보면 스펙을 상세하게 쓰고 AI 리뷰를 2중 3중으로 쌓아두면 정말 코드를 안 봐도 될 것처럼 느껴진다.

## 그럼에도 불구하고

AI는 마치 **전역이 얼마 남지 않은 말년 병장**처럼 일한다. 당장 눈앞의 문제를 해결하는 데 최선의 선택을 한다. 유지보수는 전역 이후에 누군가 신경 쓸 일인 것처럼 코드를 생산한다.

AI에게 `AGENTS.md`나 `CLAUDE.md` 같은 지침서는 권고사항일 뿐이다. 이 규칙을 꼭 지키도록 강제할 수 없다. 결국 하네스를 통해 강제해야 한다. 툴 실행 전후에 개입하는 훅(`PreToolUse`, `PostToolUse`)으로 금지된 의존성을 막거나, 반드시 별도 `worktree`에서 작업하도록 강제하는 식이다.

그런데 이런 하네스를 짜고 유지하는 것도 보통 일이 아니다. 배보다 배꼽이 더 커질 위험도 있고, 결정적으로 AI 에이전트 자신도 잘 설계된 코드(Good Design)에 의존한다.

코드가 많아질수록 복잡도는 올라갈 수밖에 없다. 개발자는 이 복잡도가 최대한 올라가지 않도록 리팩터링을 한다. 유지보수가 쉽도록 구조를 다듬지만 당장 기능 업데이트는 없다(어떤 리팩터링이냐에 따라 속도는 빨라질 수 있다). 코드 복잡도가 늘어나는 속도를 최대한 낮추면서 시스템을 키워가는 작업이다.

![AI가 모든 주도권을 가질 때와 개발자가 주도권을 가질 때의 코드 복잡성 비교](/posts/why-i-still-read-code/ai-vs-developer-ownership.png)

프로젝트가 작을 때는 AI에게 모든 주도권을 넘겨도 오히려 더 빠르고 단순해 보인다. 하지만 프로젝트가 커지고 어느 임계점을 넘어가면, '당장 돌아가는 코드'가 쌓이면서 복잡성이 가파르게 치솟는다. 그리고 이 임계점 이후엔 다시 만들어야한다. 반면 개발자가 주도권을 쥐고 구조를 다듬어 가면 초반에는 품이 조금 더 들더라도, 프로젝트가 커졌을 때 복잡성을 완만하게 붙잡아 둘 수 있다.

검토 없이 생산한 코드가 무서운 건 당장 문제가 일어나지 않기 때문이다. 예를 들어 하나로 묶일 수 있는 로직을 AI가 기존 코드를 건드리지 않으려 비슷한 클래스(또는 모듈)로 하나 더 만들었다고 해보자. 당장 한두 달은 아무 문제가 없다. 테스트도 통과하고 기능도 잘 돌아간다. 하지만 1년, 2년이 지나면서 두 클래스 각각에 의존하는 다른 객체들이 생기고, 각자에 조금씩 다른 예외 처리가 덧붙기 시작한다. 그때가 되면 둘은 비슷한 일을 하면서도 완전히 같지는 않아서 지울 수도, 쉽게 합칠 수도 없는 상태가 된다.

## 왜 이런 문제가 생길까

![기존 코드를 참고해 새 코드를 만들고 다시 코드베이스에 합류하는 AI의 개발 사이클](/posts/why-i-still-read-code/ai-development-cycle.png)

AI가 생성하는 코드가 어디서 왔는지 확인해보자. AI는 기존에 작성된 코드를 참고해 새 코드를 만들고, 그렇게 만들어진 코드가 다시 코드베이스에 쌓여 다음 작업의 참고 자료가 된다.

로렌 탄(Lauren Tan)은 강연 [All Code Is Slop (Except Mine)](https://www.youtube.com/watch?v=O_zcc6Xl12g)에서 이 구조를 "코드가 곧 AI의 메모리"라고 설명한다. 코드베이스에 임시방편이나 나쁜 패턴이 하나 들어가면, 다음 에이전트가 그걸 기존의 규칙으로 여기고 복제한다. 실제로 한 `setTimeout` 우회 코드가 5주 만에 183곳으로 번진 사례도 나온다. 그녀는 사람의 코드 리뷰를 거의 0으로 줄이는 자동화를 목표로 삼으면서도, 그 토대에는 여전히 좋은 코드 설계와 가끔은 코드를 직접 읽고 정리하는 과정을 둔다. 심지어 기존 주석의 약 99%를 지워버렸다고 하는데, AI가 임시방편을 정당화하는 도피처로 주석을 쓰고 다음 AI가 거기에 속아 넘어갔기 때문이다.

그리고 AI의 성능이 아무리 좋아져도 기능이 어떻게 늘어나고 어떤 제약이 생길지 미래를 예측할 수는 없다. 변경 가능성은 그때 가봐야 안다. 추측을 할 수 있겠지만 예지는 못한다. 결국 시스템을 계속 키워가려면 AI가 생성한 막대한 코드를 언제 어떻게 리팩터링할지 판단하고 손대는 과정이 필요하다.

## 아직은, 코드를 읽는다

그래서 하고 싶은 말이 뭐냐. AI가 코드를 써도 모든 코드를 사람이 일일이 검토하고 리뷰해야 한다는 뜻은 아니다. 이미 이렇게 높아진 생산성을 버리고 예전처럼 모든 코드를 리뷰하는 과거로 되돌아가는 건 절대 불가능하다.

나 역시 이 질문 앞에서 계속 흔들리고 있다. 불과 올해 6월까지만 해도 무조건 코드를 볼 줄 알아야 하고 직접 봐야 한다고 생각했다. 그런데 지금은 코드를 안 본다는 사람들도 많아졌고, 나 역시 최근 10만 줄짜리 프로젝트를 진행하면서 작성된 코드의 95%는 보지 않았다. "AI를 안 쓰면 도태되고, AI를 쓰면 퇴화한다"는 말이 남의 얘기 같지 않다.

그럼에도 코드를 아예 안 봐도 된다는 말에는 아직 고개를 끄덕이지 못하겠다. 모든 코드를 읽을 수는 없더라도, 문제가 생겼을 때 책임질 수 있고 복잡성이 무너지기 전에 리팩터링할 수 있을 만큼의 주도권은 쥐고 있어야 하기 때문이다.
