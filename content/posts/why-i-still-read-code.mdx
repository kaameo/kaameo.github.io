요즘 SNS를 보면 개발자들을 소위 "긁는" 어그로성 게시글이 여러개 있지만 2026년을 지나며 가장 핫했던 내용은 "아직도 코드를 보세요?" 라고 생각한다.

일단 나는 '아직은' 봐야한다는 쪽이다. 코드를 알고 이해한다는건 예측된 문제에 관해서 내가 해결 할 수 있다는것이다. 즉 내가 이 소프트웨어, 코드의 주도권을 갖고 있다는 뜻이다. 주도권을 갖고있다는건 이 코드에 대한 책임을 진다는 뜻과도 같다.

이는 마치 차량의 핸들과도 같다.

> 테슬라 사이버캡 핸들 없는데, 비슷하게 코드도 안보는 시대가 올거임

최근 테슬라에서 한화 약 4,000만원에 핸들이 없는 자율주행 차량을 일반인도 살수 있도록 한다고 한다. 약관에는 "사고나도 테슬라는 책임 안진다"라고 적혀있다.

이 두 기술은 바닥부터 다르지만, 굳이 굳이 LLM과 자율주행을 비교해봤다.

주변에서 가끔 이런 대화를 겪는다.

> **나:** 간단한 날짜 표시 기능인데 외부 라이브러리를 새로 추가하셨던데, 왜 쓰셨어요?
>
> **동료:** 그거 AI가 해준 거라 잘 모르겠어요.
>
> **나:** 아, 넵...
>
> *(5분 뒤)*
>
> **동료:** 아, 시간대 변환을 직접 짜면 버그가 잘 나서 라이브러리를 썼어요.
>
> **나:** 음, 우리 서비스는 한국 시간만 쓰는데 기본 내장 함수로도 충분하지 않나요?
>
> **동료:** 어, 잠시만요.
>
> *(5분 뒤)*
>
> **동료:** 아, 다른 모듈에서도 이미 그 라이브러리 형식으로 날짜를 주고받고 있어서 맞춰야 한대요.

우리는 이 대화를 통해서 "진짜 그럴까?"라는 생각을 가지게 된다

AI가 나오기전 개발자의 자조섞인 밈 중 JSON 상하차 라는 말이있다. 지금은 "미트 프록시"라는 말이 SNS에서 간혹 보인다.
JSON 상하차도 정말 잘 지었다고 생각했는데, AI의 답변을 직접 전달하는 생명체로 부르는게 해학의 민족이 아닐 수 없다.
위 예시에서 이사람은 개발 지식이 부족한 사람이 아니다. 코드가 어떻게 작성되어있고 어떤 아키텍처 구성인지 몰라서 이런 대답을 한다.




![영화 〈어쩔수가없다〉 (박찬욱, 2025) 中 "난 기술자야!"라고 외치는 장면](/posts/why-i-still-read-code/i-am-engineer.png)

혹시 나자신을 엔지니어라 생각하기 때문에 코드 보는걸 놓지 못하나 라는 생각도 했다.

AI가 나오면서 개발자는 한층 더 고차원의 설계를 하면 된다고 한다. 스펙만 명시하고 코드는 AI가 개발한다. 

꼭 어셈블리대신 C언어로 한층 고차원에서 개발하는거처럼 스펙만 명시한다.고 하는데, 문제는 LLM의 원리가 확률적이라는거다. 근데 그 확률이 매번 들쑥날쑥하다.

같은 C언어 파일 두개를 동시에 컴파일 돌리면 동일한 어셈블리가 나온다. 당장 AI에게 동일한 Input을 넣으면 99% 확률로 다른 output이 나올거다

이건 계산기로 비유를 들 수 있다. 계산기가 있음에도 우리가 수학을 배우는 이유는 단순히 계산을 하기 위해서가 아니다.

jev 처럼 선택하는 모델같은 경우엔 웬만하면 거의 동일한 output이 나온다고 하는데, 이 선택 모델쪽이 사람의 기대를 충족시키기때문에 선택모델쪽이 발전할 가능성이 더 클거같다.

그리고 결론적으로 계산기는 같은 입력에 같은 출력이 나온다.

> 그건 스펙을 너무 모호하게 써서 그럼

이 소프트웨어, 시스템의 스펙을 자연어로 적으면서 모호함을 없애기위해 상세하게 적으면, 그게 결국 코드가 된다.

[Should we still design code for humans?](https://www.thoughtworks.com/insights/blog/programming-languages/should-still-design-code-humans)

근데 결국 AI로 끌어올린 생산성에 사람이 검토하는게 병목인 이 상황에서 리뷰한다고 병목을 굳이 만들어야되나 하는 생각도 있다.
결국은 AI가 만들어내는 막대한 코드를 최대한 따라가야 한다. 나만 그렇게 느낀건 아닌지 이런 문제를 해결하기 위해 나온 몇가지를 사용하고 있다.
sphinx(https://github.com/parthh01/sphinx), teach me 등등..

[Harvard 연구진, AI 코딩 에이전트가 병목을 코드 리뷰로 옮겼음을 확인](https://news.hada.io/topic?id=37405)

"AI 코드리뷰를 2중 3중으로 두면 결국 버그는 찾는다" 나도 공감한다. 결국 2중 3중으로 AI를 돌리면 버그는 찾아진다고 느낀다. 

문제는 스펙을 상세하게 쓰고 AI 리뷰를 2중3중으로 쌓아두면 문제가 없다.

한가지 남은 문제는 AI는 전역이 얼마 남지 않은 말년 병장처럼 일을 한다는것이다. 

AI에게 AGENTS.md, CLAUDE.md 같은 프롬프트는 권고사항일 뿐이다. 이 지침서를 꼭 지키도록 강제할 수 없다.
이땐 하네스를 통해 강제해야 한다. 의존하지 말아야할것을 PostToolUse를 통해 강제하거나 PreToolUse로 worktree에서 작업하도록 강제할 수 있다.

근데 이런 하네스를 짜는것도 보통일이 아니다. 배보다 배꼽이 더 커질 위험도 있고, 결정적으로 AI 에이전트도 잘 설계된 코드(Good Design)에 의존한다.

로렌탄의 강연[All Code Is Slop (Except Mine)](https://www.youtube.com/watch?v=O_zcc6Xl12g)에서는 AI가 완전히 작업할 수 있도록 강제하는 하네스 얘기를 한다.

코드가 많아질수록 코드의 복잡도를 무조건 올라갈수 밖에 없다. 개발자는 이 복잡도가 최대한 올라가지 않도록 리팩터링이란걸 한다.

유지보수가 쉽도록 하지만 아무런 기능 업데이트는 없다.(어떤 리팩터링이냐에 따라 속도는 빨라질 수 있다)

AI는 마치 말년병장처럼 지금 순간에 최선의 선택을 한다. 유지보수는 전역 이후에 신경쓸것처럼 코드를 생산한다.

결국 개발자는 앤트로피가 늘어나는 속도를 최대한 낮추면서 시스템을 키워가야 한다. 그러려면 AI가 생성하는 막대한 코드를 리팩터링해줘야한다.

AI는 개발할때 본인만의 사이클이 있다. 기존 작성된 코드를 참고해서 다시 개발한다. 이 과정은 로렌 탄에서 잘 나오니 확인해보길 바란다.

로렌 탄의 강연에서도 초반 어느정도는 코드를 직접 보며 AI가 참고할 코드를 정리한다. 또 주석도 거의 다 제거해 버렸다. (클린코드의 주석금지는 정답이였나?)

AI의 성능이 아무리 좋아져도 기능이 어떻게 늘어나고 어떤 제한을 가질지 미래를 예측할 수는 없다. 즉 변경 가능성은 그때 가봐야 안다. 추측은 하지만 예지는 못한다.

불과 올해 6월까지만 해도 무조건 코드 볼줄 알아야하고 봐야된다 생각을 가지고 있었다. 지금은 코드를 안본다는 사람들도 많고 나도 프로젝트를 진행하면서 작성한 코드중 95%의 코드를 안봤다.
해당 프로젝트는 10만줄이였다.

"AI를 안쓰면 도태되고, AI를 쓰면 퇴화한다." 도 요즘 핫하다. 결국 AI가 생성한 이 코드들을 리팩터링하고 변경할지 코드를 직접 보는 과정이 필요하다.
