## TL;DR

- EC2 두 대(`t3.large` + `t3.medium`)로 만든 k3s 클러스터에 Spring Boot 앱 6개와 데이터·관측성 스택이 꽉 차 있었다. 새 기능(AI·검색·알림)을 올릴 메모리가 없었다.
- 운영 지표를 쪼개 보니 범인은 heap이 아니었다. JVM 앱 하나가 **off-heap(Metaspace·JIT 코드 캐시·Native)으로만 280~355MiB를 상시** 쓰고 있었다.
- 트래픽이 가장 적은 `customer-support-app` 하나를 **GraalVM Native Image**로 바꿔 메모리 limit을 448Mi에서 256Mi로 낮추고, `t3.medium` 노드에 192Mi의 배치 여유를 확보했다.
- 다만 CI 빌드 시간이 10~14분 늘고 수동 메타데이터 관리 부담이 생겨, 나머지 5개 앱은 JVM으로 남기기로 결정했다.

## 1. 배경: 늘릴 수 없는 EC2 두 대

합방 백엔드는 Java 25, Spring Boot 4.1.1 기반의 독립 앱 6개(`member`, `billing`, `appearance`, `lecture`, `chat`, `customer-support`)로 나뉘어 있다. 주어진 AWS 리소스는 `t3.large`(8GiB) 1대와 `t3.medium`(4GiB) 1대가 전부였고, 그 위에 k3s 클러스터 하나를 올려 모든 앱과 인프라를 함께 돌리고 있었다.

<Cluster {...k3sCluster} />

여기에 AI(RAG), 통합 검색, 알림 세 기능을 더 올려야 했다. 하지만 앱 pod는 request와 limit을 같게 두고 있어서 `t3.medium`의 request 여유는 이미 312Mi뿐이었고, 6개 앱 모두 7일 최대 working set이 limit의 85~100%에 붙어 있었다.

<Chart {...workingSet7d} />

여유가 거의 없던 `billing`과 `Grafana`를 먼저 512Mi로 올리고 나니, `t3.medium`의 남은 공간은 248Mi까지 줄었다. 기존 앱의 메모리를 줄이지 않으면 새 앱을 띄울 수 없는 상황이었다.

---

## 2. 원인: 범인은 Heap이 아니라 Off-heap이었다

메모리가 꽉 차 있으면 "heap을 줄이자"가 첫 반응이다. 그런데 Prometheus의 JVM 지표(`jvm_memory_*`)와 컨테이너 지표(`container_memory_*`)를 나란히 쪼개 보니 그림이 완전히 달랐다.

6개 앱의 실제 heap 사용량(7일 최대)은 82~154MiB에 불과했다. 대신 heap 밖의 메모리(RSS − heap committed)가 앱마다 **280~355MiB씩 상시** 잡혀 있었다. 게다가 `-XX:MaxRAMPercentage=60` 설정 탓에, heap이 상한까지 커지면 6개 앱 모두 컨테이너 limit을 76~119MiB 초과하는 위험한 구조였다.

<Chart {...heapAtMax} />

off-heap 280~355MiB의 정체는 크게 세 덩어리였다.

- **Metaspace (130~152MiB)**: Spring, Hibernate, Kafka, Tomcat 등 앱마다 로드되는 클래스 2.6만~3만 개의 메타데이터
- **JIT 코드 캐시 (20~43MiB)**: 실행 중 JIT가 컴파일해 둔 기계어
- **Native (117~163MiB)**: 스레드 60~106개의 스택, glibc malloc arena, GC 자료구조 등

JVM을 쓰는 한 앱을 하나 띄울 때마다 이 고정 비용을 매번 다시 내야 한다. 반면 **GraalVM Native Image**는 빌드 시점에 AOT(Ahead-of-Time)로 기계어를 미리 만들어 두기 때문에, 런타임에 Metaspace와 JIT 코드 캐시가 통째로 사라진다.

<MemoryAnatomy />

다만 전체 앱을 한꺼번에 바꾸기에는 리스크가 컸다. 트래픽이 가장 적고 외부 연동도 단순하지만 JPA·Flyway·Kafka·Spring Modulith·Spring Security·Resilience4j를 모두 쓰는 **`customer-support-app` 하나만 먼저 전환해 재 보기로 했다.**

## 3. 전환: 빌드 때 굳고, 실행 때 터진다

Native Image는 "닫힌 세계(closed world)"를 가정한다. 빌드 시점에 보이지 않는 reflection, 리소스 파일 읽기, Java 직렬화는 미리 알려 주지 않으면 실행 중에 그대로 실패한다.

기존 테스트 코드(212개)는 한 줄도 고치지 않고 JVM 회귀 테스트로 두고, 실제 API·Kafka·내부 HTTP 호출을 밟는 smoke 스크립트를 JVM+AOT, macOS native, Linux native에 똑같이 돌려 5건의 문제를 찾아 고쳤다.

<MigrationPipeline />

빌드 설정에서 가장 중요했던 두 가지는 **`processAot`에 운영 프로필을 고정하는 것**과 **`sharedLibrary = false` 명시**다. Spring AOT는 `@Profile`과 `@ConditionalOnProperty`를 빌드 시점에 평가해 빈을 확정하므로, 운영 전용 포트(내부 API 8081, actuator 8082)를 빌드 인자로 넘겨야 했다. 또 루트에 `java-library` 플러그인이 걸려 있으면 Native Build Tools가 실행 파일 대신 공유 라이브러리(`.so`)를 기본으로 만든다.

```kotlin
// apps/customer-support-app/build.gradle.kts
tasks.named<org.springframework.boot.gradle.tasks.aot.ProcessAot>("processAot") {
    args(
        "--spring.profiles.active=prod",
        "--hapbang.internal-api.port=8081",
        "--management.server.port=8082",
    )
    environment(mapOf("LECTURE_API_BASE_URL" to "http://lecture-app:8081" /*, DB_URL 등 */))
}

graalvmNative {
    binaries.named("main") {
        imageName = "app"
        mainClass = springBoot.mainClass
        sharedLibrary = false
    }
}
```

운영 배포 뒤 256Mi로 내릴 때 겪은 함정도 하나 있었다. Native 실행 파일은 환경 변수 **`JAVA_TOOL_OPTIONS`를 읽지 않는다.** 기본 heap 상한이 컨테이너 메모리의 80%(256Mi 기준 약 205Mi)로 잡혀 off-heap과 합치면 OOM 위험이 있었다. `-Xmx24m`을 환경 변수와 실행 인자로 각각 넣어 GC 로그를 확인한 뒤, 운영 Deployment `args`로 `-Xmx128m`을 직접 넘겨 해결했다.

## 4. 결과: 메모리 절반, 기동 20배

운영 값은 JVM(오래 돈 pod)과 Native(전환 뒤 관측)의 기간과 부하가 다르다. 그래서 공정한 비교는 로컬에서 운영과 같은 조건(Serial GC, 2 vCPU, `-XX:MaxRAM=448m -XX:MaxRAMPercentage=60`)으로 맞춰 쟀다.

<Chart {...rssComparison} />

기동 직후, 작업 직후, 60초 idle 세 시점 모두 Native의 RSS가 **44~45% 작았다.** 로컬 기동 시간도 4.3초에서 0.57초로 줄었다.

운영에 배포하고 5시간 실측(working set 142~174Mi, heap 최대 84Mi)을 확인한 뒤, request와 limit을 448Mi에서 256Mi로 낮추고 `-Xmx128m`을 적용했다. 이후 약 17시간 동안 재시작은 0회였고, working set 최대 123Mi(limit의 48%), RSS 최대 80Mi, heap 최대 52Mi로 안정적이었다. 30시간 Loki 로그에서도 native 전용 오류는 0건이었다.

<Chart {...limitReduction} />

메모리 외에도 운영 지표 세 가지가 함께 달라졌다. 특히 `t3.medium`은 여유 공간이 없어 기존 pod를 내린 뒤 새 pod를 띄우는(`maxSurge: 0`) 상태였는데, 기동이 25초에서 1.1초로 줄면서 배포 중단 시간도 크게 줄었다.

## 5. 트레이드오프: 왜 하나만 남겼나

메모리 그래프만 보면 나머지 5개 앱도 다 바꾸고 싶어진다. 하지만 전환 직후 가장 먼저 체감한 벽은 **CI 빌드 시간과 자원**이었다.

<Chart {...ciJobTime} />

다른 앱 job이 3~6분이면 끝날 때, `customer-support` 하나만 13~18분을 붙잡고 있었다. GitHub 러너(4 vCPU, 16GB)에서 컴파일 Peak RSS가 12.2GB까지 올라가 메모리 여유도 빠듯했다. 배포 파이프라인은 6개 앱이 모두 성공해야 배포되기 때문에, 공용 모듈을 건드리는 PR마다 팀 전체의 대기 시간이 늘었다.

런타임에서 얻은 것과 빌드·개발·운영에서 잃은 것을 나란히 놓아 보면 트레이드오프가 뚜렷하다.

<TradeoffBoard />

그래서 **확대를 보류하고 `customer-support-app` 하나만 Native로 유지하기로 했다.** 앱마다 CI가 10~14분씩 늘고, 앱마다 tracing agent와 smoke 검증을 유지하는 비용이 메모리 절감 효과보다 컸다.

<DecisionQuadrant />

나머지 JVM 앱은 비율 설정(`MaxRAMPercentage`) 대신 앱별 `-Xmx`와 native 메모리 튜닝을 먼저 적용하기로 했다. AI·검색·알림을 묶어 새로 만드는 `aux-app` 역시 Spring AI·OpenAI·Elasticsearch 클라이언트가 한꺼번에 들어가고 변경이 잦아 JVM으로 띄우기로 결정했다.

## 6. 돌아보며

1. **메모리가 모자라면 감으로 추측하지 말고 쪼개 본다.** heap이 아니라 off-heap의 상시 고정 비용이 핵심이었고, 작은 컨테이너에서 `MaxRAMPercentage=60`은 OOM을 부르는 설정이었다.
2. **JVM 테스트 통과는 Native 동작을 보장하지 않는다.** 설정 파일 누락, record 직렬화, Kafka 예외 직렬화 모두 JVM에서는 멀쩡했다. 실제 경로를 밟는 smoke 스크립트와 tracing agent가 없었으면 운영에서 터졌을 문제들이다.
3. **도구 기본값과 옵션 적용 여부를 직접 확인한다.** `java-library` 때문에 `app.so`가 나오고, `JAVA_TOOL_OPTIONS`가 Native에서 무시되는 문제는 30초짜리 작은 실험으로 확인해야 놓치지 않는다.
4. **전면 도입 전에 가장 작은 앱 하나로 비용을 먼저 잰다.** 파일럿 하나로 메모리 절감 효과뿐 아니라 CI 13~18분, 러너 12GB, 관측 제약이라는 실제 가격표까지 얻었기에, 어디서 멈출지 근거 있게 판단할 수 있었다.
