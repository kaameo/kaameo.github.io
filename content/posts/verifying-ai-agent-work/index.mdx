## TL;DR

- 팀 프로젝트 합방의 [백엔드 저장소](https://github.com/prgrms-be-adv-devcourse/beadv8_8_LMS_BE)에서 내가 올린 PR 186개를 Claude Code와 함께 만들었다. 코드는 에이전트가 쓰되, **계획 → 테스트 → 리뷰** 세 단계에서 방향과 결과를 확인하는 흐름으로 진행했다.
- 가장 효과가 컸던 건 리뷰 단계였다. GitHub Actions에서 도는 Claude 리뷰가 diff 바깥의 팀 문서와 설정까지 대조하도록 프롬프트를 고친 뒤, 인라인 지적이 달린 내 PR 비율이 11%에서 77%로 뛰었다. 그렇게 달린 지적 69건 중 64건은 실제 코드 수정으로 이어졌다.

## 계획

에이전트에게 이슈 번호만 던져 주면 바로 코드를 고치기 시작한다. 요구사항을 잘못 짚은 채로 구현부터 달리면 나중에 PR을 통째로 뜯어고쳐야 해서, 애초에 코드를 만지기 전에 생각을 맞추는 쪽으로 틀을 잡았다. 

매번 같은 프롬프트를 치기 번거로워 이슈 번호만 넘기는 [`/plan-ticket`](https://gist.github.com/kaameo/dfff6403a1f2115536d0076c1bca9488) 커맨드를 만들어 썼다.

**내가 플랜을 승인하기 전까지는 읽기·조회만 한다.** 에이전트는 이슈의 완료 조건과 관련 문서, 기존 코드를 읽은 뒤 단계별 플랜을 낸다. 이때 각 단계가 어떤 완료 조건을 만족시키는지 번호를 달게 했고, 작업 성격에 맞춰 [mattpocock/skills](https://github.com/mattpocock/skills)의 스킬을 함께 걸었다.

- `grilling`: 애매한 부분을 에이전트가 멋대로 추측하지 말고 먼저 물어보게 한다. 보통 한 번에 질문이 10개 안팎 들어온다.
- `domain-modeling`, `codebase-design`: 팀에서 쓰는 용어와 맞는지, 다른 모듈과 어디를 연결하고 어디를 끊을지 미리 짚고 넘어간다.

질문이 항상 쉽게 풀리진 않았다. [지갑 앱 HTTP 클라이언트를 붙이는 작업](https://github.com/prgrms-be-adv-devcourse/beadv8_8_LMS_BE/issues/272)에서는 질문 네 개 중 셋은 추천안대로 넘겼는데, 하나는 에이전트가 무슨 뜻으로 물었는지 자체가 이해가 안 돼서 그대로 되물었다.

> 이해 안돼 다시 설명해

설계 방향이 아예 바뀐 경우도 있다. [강의 AI 추천 동기화 작업](https://github.com/prgrms-be-adv-devcourse/beadv8_8_LMS_BE/issues/712)에서 에이전트가 장바구니와 리뷰에 낙관적 락(`@Version`)만 달자고 했는데, 동시에 두 요청이 들어오면 두 번째 요청이 500 에러로 떨어지는 게 된다. version만 달면 되는지 다시 따져 묻고 선택지를 받아 본 끝에 행 잠금을 같이 쓰는 쪽으로 바꿨다. 그리고 그 결정이 코드에 남도록 테스트 항목도 플랜에 바로 끼워 넣었다.

> 장바구니 빼기, 리뷰 수정을 동시에 두 번 해도 둘 다 성공하는지 확인하는 테스트 추가.

## 테스트

승인하고 나면 플랜에 적어 둔 테스트부터 만든다. 실제로 승인한 플랜에는 단계마다 테스트 이름이 아래처럼 붙어 있다.

```text
4. [C2·C3·C4] LectureSyncEvents.lectureChanged와 Lecture.toSyncDto()를 만들고, 강의 use case 7곳에서 부른다.
   - 강의를_등록하면_version_0과_콘텐츠로_이벤트가_나간다
   - 콘텐츠만_바꿔도_강의_version이_오르고_새_콘텐츠로_나간다
   - 삭제하면_deleted_true_onSale_false로_나간다
```

구현은 `tdd` 스킬로 실패하는 테스트를 먼저 쓰고 통과시키는 순서로 돌렸다. 다만 테스트가 초록불이라고 해서 내 의도대로 검증되고 있다는 보장은 없다. 껍데기만 통과하는 테스트를 거르려고, 중요한 부분은 구현 코드를 일부러 되돌렸을 때 테스트가 정말 깨지는지 확인했다.

단위 테스트를 붙이기 어려운 인프라 작업은 단계마다 실행할 검증 명령어와 기대 결과를 플랜에 적어 두고 그걸 확인하는 식으로 대체했다.

## 리뷰

GitHub Actions로 [PR마다 도는 Claude 리뷰 워크플로우](https://github.com/prgrms-be-adv-devcourse/beadv8_8_LMS_BE/pull/212)를 붙였다. 처음에 넣어 둔 기준은 `AGENTS.md`의 모듈 경계와 결제·금액 규칙 두 가지뿐이었다.

그런데 3주쯤 굴려 보니 영 쓸모가 없었다. 리뷰 한 번이 평균 22초 만에 끝났고, diff 바깥의 다른 파일을 열어 보는 횟수가 0~2번에 그쳤다. 10월 15일부터 11월 5일까지 리뷰된 내 PR 91개 중 인라인 지적이 달린 건 10개(11%)뿐이었다. 반대로 Claude가 문제없다고 넘어간 PR 4개에서 CodeRabbit이 지적 7건을 잡아냈다.

쿠버네티스 설정을 고친 한 PR에서는 Claude가 diff 안의 메모리 합계만 맞춰 보고 통과시켰는데, CodeRabbit은 다른 앱의 k8s 매니페스트(`apps/*/k8s`)까지 뒤져서 최대 surge 메모리가 640Mi가 아니라 704Mi라는 걸 찾아냈다.

diff 내부만 보면 그럴듯해 보인다. 문제는 diff 외부의 팀 문서나 다른 앱 설정, 예전에 정해 둔 규칙과 어긋날 때 생긴다. 그래서 11월 5일에 [CI 리뷰 프롬프트를 전면 수정](https://github.com/prgrms-be-adv-devcourse/beadv8_8_LMS_BE/pull/701)했다.

- 바뀐 파일 성격에 맞는 팀 문서를 직접 골라 읽게 했다. 로그를 고쳤으면 `logging.md`, 쿠버네티스 설정이면 `k8s.md`를 읽는 식이다.
- diff에 나오는 숫자, 이름, 설정 키는 grep으로 다른 코드, 설정, 문서와 대조하게 했다.
- 테스트가 추가됐으면 실제로 의도한 실행 경로를 타는지 따져 보게 했다.
- 기준 문서는 PR 브랜치가 아니라 `dev` 브랜치에서 읽어 오게 했다. `AGENTS.md`를 건드린 PR이 자기 리뷰 기준까지 같이 바꿔 버리는 걸 막기 위해서다.

<ReviewChart />

프롬프트를 바꾼 뒤 인라인 지적이 달린 PR 비율은 11%(91개 중 10개)에서 77%(39개 중 30개)로 올랐다. 댓글 수로는 11건에서 69건이 됐다.

물론 지적이 많아졌다고 다 맞는 말은 아니어서, 달린 댓글 69건을 실제로 어떻게 처리했는지 확인했다. 42건은 그대로 고쳤고, 22건은 일부만 반영하고 나머지는 수정하지 않는 이유를 코멘트로 달았다. 고치지 않고 이유만 남긴 건 2건이었다. 69건 중 64건이 실제 수정이 필요했다.

그중 제일 기억에 남는 건 트랜잭션 격리 수준을 다룬 PR에 달린 ["`REPEATABLE_READ` 효과를 검증하는 테스트가 없다"는 지적](https://github.com/prgrms-be-adv-devcourse/beadv8_8_LMS_BE/pull/721#discussion_r4488531460)이었다. 누군가 `isolation` 설정을 지워도 기존 테스트가 전부 통과한다는 얘기였다. 바로 테스트를 추가하고 `isolation`을 뺐을 때 실제로 실패하는 것까지 확인했다. 프롬프트에 넣은 테스트 검증 규칙이 의도대로 먹힌 대표적인 사례다.

## 아쉬웠던 점

이 흐름이 매번 깔끔하게 굴러간 건 아니다.

계획 단계부터 깊이가 들쭉날쭉했다. `/plan-ticket`으로 코드 수정까지 간 약 20번 중 9번 가까이는 질문에 선택지만 고르거나 "추천대로", "승인" 한마디로 넘겼다. 바쁘거나 익숙한 작업일수록 꼼꼼히 따져 보는 힘이 빠졌다.

테스트 역시 에이전트에게 맡겨 두고 끝낼 수 없었다. 테스트가 있더라도 내가 확인하려던 조건을 진짜로 검증하는지, 경계 조건이 빠져 있지는 않은지 결국 눈으로 한 번 더 훑어야 했다.

리뷰도 문서와 코드의 불일치를 끝까지 잡아내지는 못했다. 프로젝트 문서가 늘어날 수록 내용이 깔끔하게 나뉘지 않았다. 예를 들어 로깅 구현 내용이 모니터링 문서에 섞여 들어간 경우에는 `logging.md`만 읽어서는 놓치는 부분이 생겼다.
그리고 문서마다 같은내용을 다르게 정한 불일치도 있었다.

## 결론

구현 자체는 대부분 AI가 했지만, 플랜을 따져 묻고 테스트가 진짜 실패하는지 확인하고 리뷰 기준을 고치는 건 결국 내가 계속 붙잡고 있어야 했다. 아직 손이 많이 가지만, 혼자서 PR 186개를 쳐내면서 사고를 줄이는 데는 이 정도 장치가 꽤 도움이 됐다.
