## 요약

TDD 입문서로 아주 좋은 책이다. AI 에이전트가 많은 코드를 작성하는 지금 시대에 TDD를 아는 것은 필수라고 생각한다.

AI가 코드를 작성해 주더라도 책임은 개발자에게 있다. 모든 구현 코드를 세세하게 점검하기 어렵다면 최소한 테스트가 내가 원하는 동작을 제대로 표현하는지 확인해야 한다. 테스트에 개발자가 구현하려는 기능의 의도가 잘 담겨 있다면 검토의 부담도 줄일 수 있다.

## 후기

AI 에이전트가 코드의 대부분, 거의 전부를 작성하는 지금의 개발 사이클에서 테스트가 그 어느 때보다 중요해졌다. 자연어로 작성한 요구사항에는 해석의 여지가 있어 모호할 수밖에 없다. 코드가 만족해야 할 조건을 가장 구체적으로 표현하는 방법은 결국 테스트다.

### TDD 간략 설명

TDD에서 가장 중요한 것은 다음 사이클을 반복하는 것이다. 이를 Red-Green-Refactor 사이클이라고 한다.

1. 테스트를 작성하고 실행해 실패하는 것을 확인한다.
2. 테스트를 통과하는 최소한의 코드를 작성한다.
3. 테스트가 통과하는 상태를 유지하며 코드를 리팩터링한다.

두 파라미터를 받아 더한 값을 반환하는 `add` 메서드를 만든다고 가정한다. 그러면 테스트를 다음과 같이 작성할 수 있다.

```java
class CalculatorTest {
  @Test
  void add() {
    int result = Calculator.add(1, 2); // ①

    assertEquals(3, result);
  }
}
```

① 한 줄을 작성하는 것만으로도 개발자는 여러 가지를 결정해야 한다.

- 메서드를 제공할 클래스의 이름으로 `Calculator`가 적절한가?
- 메서드의 이름으로 `add`가 의도를 잘 나타내는가?
- 파라미터의 개수와 타입이 적절한가?
- 정적 메서드로 제공할 것인가, 인스턴스 메서드로 제공할 것인가?

테스트를 먼저 작성하면 구현하는 사람의 관점이 아니라 사용하는 사람의 관점에서 API를 생각하게 된다.

### AI 개발에서 TDD

> "테스트도 AI한테 맡기면 되죠."

AI가 테스트를 대신 작성해 주더라도 책임은 개발자에게 있다. 테스트가 요구사항을 제대로 표현하는지, 경계 조건과 예외 상황도 다루는지, 구현 방식에 지나치게 의존하지 않는지 검토해야 한다. 잘못된 테스트를 기준으로 구현하면 AI는 잘못된 목표를 향해 빠르게 달려간다.

### 이 책이 좋았던 점

이 책은 예제를 통해 TDD가 무엇인지, TDD 사이클이 무엇인지 쉽게 이해할 수 있게 설명한다. 테스트를 먼저 작성하고, 실패를 확인하고, 테스트를 통과시키기 위한 코드를 구현하는 과정을 차근차근 따라갈 수 있다. TDD를 단순히 테스트 코드를 작성하는 기술이 아니라 설계를 개선하는 반복 과정으로 이해하는 데 도움이 됐다.

이 글에서는 TDD 사이클만 다뤘지만, 테스트 대역(Test Double)이 왜 필요하고 잘 작성된 테스트가 무엇인지도 이 책에서 잘 설명해 준다.

Red-Green-Refactor 사이클을 아직 모른다면 꼭 한 번 읽어보길 권한다. 특히 AI 에이전트에게 구현을 맡기면서 무엇을 어떻게 검증해야 할지 고민하는 개발자에게 좋은 출발점이 될 거라 생각한다.
